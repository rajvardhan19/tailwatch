# API, keys, subscriptions and email delivery

C27–C28 use FastAPI and PostgreSQL. Construct `create_app(engine)`; production exposure is disabled by default. API keys are random 256-bit bearer tokens, stored only as SHA-256 digests, tenant-scoped, independently revocable and separated into customer/analyst scopes. Provision tenants and keys through an operator session with `issue_key`; return the secret once. Never place keys in URLs or logs. Serve behind HTTPS and a request-rate/body-size limiting reverse proxy before public deployment.

Customer routes list approved alerts with bounded UUID cursor pagination, expose sanitized approved/superseded/outcome history, replace/read/remove watchlist entries by stable company UUID, and revoke the caller's key. Analyst review requires separate scope plus explicit human confirmation. Internal draft notes never become customer prose. Use C05 historical ticker resolution before adding a company; this API deliberately accepts stable UUIDs, not ambiguous ticker strings.

Subscriptions are created unverified with hashed confirmation/unsubscribe tokens. `subscribe` returns tokens only to the trusted verification-message workflow, never to an untrusted customer claiming an arbitrary address. `verify_subscription` and `unsubscribe` check tokens. An independently configured verification message workflow is needed before enabling public subscription signup. CI uses reserved `.invalid` addresses and a stub; no messages are sent.

`enqueue` requires the same tenant, an active verified subscription and current approval, and deduplicates the approval/subscription key. `deliver_one` durably claims the item before sending, then locks the episode and subscription through its final state check and provider call. Supersession or unsubscribe before this check cancels delivery. An unsubscribe racing an already-started send takes effect after that attempt; it cannot recall sent mail. External sending rejects synthetic alerts and requires a live-release guard. The sender is Resend over HTTPS with a stable idempotency key. Its published idempotency retention is limited, not an exactly-once guarantee.

Timeouts and missing acknowledgments become uncertain. A crash after claim leaves sending state; `reconcile_abandoned` marks stale attempts uncertain. Do not automatically retry uncertain deliveries after provider idempotency expiry; reconcile against provider evidence and record the operator decision. Logs must never contain provider credentials, confirmation tokens or recipient payloads. Production release must configure verified sender/domain, daily quota, unsubscribe instructions, monitoring and source evidence rights before any real sender is enabled.

## Operator provisioning and destination controls

`tailwatch provision-workspace --name NAME --email ADDRESS --output /private/path/new-credentials.json` creates a tenant, customer key and unverified subscription in the configured migrated database. The output file is created exclusively with owner-only permissions; existing files/symlinks are never replaced. Standard output contains identifiers and the file path only. No verification or notification email is sent. Keep this file out of version control and deliver the verification token only to the intended recipient through your configured trusted channel, separately from customer-key distribution. Do not hand a customer the combined operator file for an arbitrary address.

Recipients POST a JSON `token` to `/subscriptions/{id}/verify` or `/subscriptions/{id}/unsubscribe`. Verification expires after 24 hours and is single-use; unsubscribing remains available without an API key. Tokens are not accepted in URLs. Authenticated customers can list their own subscriptions (bounded cursor pagination) and disable one with DELETE `/subscriptions/{id}`. Neither listing nor errors return token hashes. These routes do not offer public signup or automatic verification email: a verified sender/domain and rate-limited verification dispatch remain deployment dependencies.
